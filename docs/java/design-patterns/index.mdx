## Pattern selection guide

The fastest way to recognize a pattern is by **the smell** that suggests it.

| You hear / feel... | Reach for... | Family |
| --- | --- | --- |
| "Different algorithms for the same task" | Strategy | Behavioral |
| "Create one of many concrete types" | Factory Method / Abstract Factory | Creational |
| "Step-by-step construction with many optional parts" | Builder | Creational |
| "One instance per JVM" | Singleton (sparingly — DI containers usually do this) | Creational |
| "Need to add behaviour without changing the class" | Decorator | Structural |
| "Wrap a complex subsystem" | Facade | Structural |
| "Lazy / access control / interception" | Proxy | Structural |
| "Notify listeners when something changes" | Observer | Behavioral |
| "Sequence of handlers, each may handle or pass on" | Chain of Responsibility | Behavioral |
| "State-dependent behaviour, lots of `if`s on a state field" | State | Behavioral |
| "Need undo / redo or to queue actions" | Command | Behavioral |
| "Encapsulate traversal" | Iterator | Behavioral |
| "Centralize many-to-many coupling" | Mediator | Behavioral |
| "Add an operation to a class hierarchy without modifying it" | Visitor | Behavioral |
| "Capture and restore object state" | Memento | Behavioral |
| "Treat individual objects and compositions uniformly" | Composite | Structural |

## Interview gotchas

- **Strategy vs. State** look identical structurally — the difference is *intent*. Strategy is "pick one and stick with it for this call"; State is "the object's behaviour changes as it transitions."
- **Decorator vs. Proxy** — Decorator adds *new* behaviour; Proxy controls *access* to the same behaviour.
- **Singleton in tests** poisons isolation. Spring beans (singleton by default) are okay because the framework controls their lifecycle. Hand-rolled `INSTANCE` fields rarely are.
- **Patterns aren't goals.** Name a pattern only when it makes the design clearer. "Forced pattern" is worse than "no pattern."
- **Composition over inheritance** — most GoF patterns prefer composition because inheritance is a tight bind.

## Q&A quick reference

| Question | Quick answer |
| --- | --- |
| Strategy vs. State? | Same shape, different intent: pick-once vs. mutate-over-time. |
| Adapter vs. Decorator? | Adapter changes the interface; Decorator wraps the same interface. |
| Why is Singleton an anti-pattern? | Global mutable state, hard to test. Spring beans are okay; hand-rolled rarely. |
| What pattern does Spring `@Transactional` use? | Proxy. The bean call goes through a proxy that begins / commits the tx. |
| Difference between Saga and 2PC? | 2PC blocks; Saga uses compensating actions — modern microservices answer. |
| What's hexagonal architecture? | Domain depends on **ports**; **adapters** implement ports. Replaceable infra. |
| Why prefer composition over inheritance? | Inheritance is a tight bind; composition gives runtime flexibility. |
