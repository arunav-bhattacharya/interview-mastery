## 6.1 Why evaluations are everything

The frontier-model providers iterate fast. The frameworks change. What persists is the discipline of *measuring whether your system is getting better or worse*. Evals are how you do that.

Three distinctions that prevent confusion later:

- **Offline evals** run against a fixed dataset. Cheap, repeatable, useful as a CI gate.
- **Online evals** measure live traffic — user thumbs, regret rate, downstream conversion. Slow but reflect reality.
- **Eval datasets** ≠ *training data*. Training data teaches the model; eval data is held out so you can tell whether changes help.

Hamel Husain's *LLM Evals FAQ* is the single best primer in the field. Bookmark it; you'll come back to it for years.

## 6.2 Build evaluations

The flow that produces useful evals — applied to the agent you built in Week 4:

**Step 1 — Manual labeling.** Run your agent on 100 real or realistic queries. Paste the inputs, outputs and traces into a spreadsheet. For each, label PASS or FAIL and write a one-line note about *why* it failed.

**Step 2 — Failure clustering.** Read your 100 traces and group failures into 5–8 categories: *wrong tool chosen*, *tool returned but model ignored the result*, *hallucinated citation*, *got stuck in a loop*, *exceeded token budget*. These categories are your evaluation surface.

**Step 3 — LLM-as-judge per failure mode.** For each category, write a tiny LLM prompt that takes (input, output, expected) and returns PASS / FAIL with a one-line rationale. Test each judge on your manually-labeled set and measure **TPR** (when it should say FAIL, does it?) and **TNR** (when it should say PASS, does it?). A judge with TPR > 0.85 and TNR > 0.85 is usable.

<CodeTabs python={`# A single LLM-as-judge for "wrong tool chosen"
import anthropic
client = anthropic.Anthropic()

JUDGE_PROMPT = """You are evaluating whether an AI agent chose appropriate tools.

User question: {question}
Tools called: {tool_calls}
Final answer: {answer}

Did the agent choose tools that were necessary and sufficient to answer?
Reply with exactly one line: 'PASS — <reason>' or 'FAIL — <reason>'."""

def judge_tool_choice(question, tool_calls, answer) -> tuple[bool, str]:
    resp = client.messages.create(
        model="claude-haiku-4-5-20251001", max_tokens=100,
        messages=[{"role": "user", "content": JUDGE_PROMPT.format(
            question=question, tool_calls=tool_calls, answer=answer)}],
    )
    text = resp.content[0].text.strip()
    return (text.startswith("PASS"), text)`} />

**Step 4 — Golden dataset.** Pick 20–30 of your labeled examples as a *golden set*: cases you commit to never regressing on. Wire them into CI — every prompt or code change has to pass them before merging.

**Step 5 — Iterate.** Now changes have signal. You can A/B prompts, swap models, tune retrieval — and the evals tell you whether it actually helped.

## 6.3 Observability

You need three things logged for every LLM call: cost, latency, and tool calls. Langfuse gives you all three with a one-line decorator.

<CodeTabs python={`from langfuse.decorators import observe, langfuse_context
import anthropic

client = anthropic.Anthropic()

@observe()
def answer(question: str) -> str:
    resp = client.messages.create(
        model="claude-sonnet-4-6", max_tokens=300,
        messages=[{"role": "user", "content": question}],
    )
    langfuse_context.update_current_observation(
        input=question, output=resp.content[0].text,
        usage={"input": resp.usage.input_tokens,
               "output": resp.usage.output_tokens},
    )
    return resp.content[0].text`} />

Build a dashboard that surfaces:
- Cost per session and per user.
- p50 / p95 / p99 latency by endpoint.
- Tool-call frequency and failure rate per tool.
- Failed-eval rate over the last 24 hours (using your judges from §6.2 sampled on production traffic).

The single most useful dashboard is "failed tool calls grouped by tool" — it tells you exactly which integration is rotting first.

## 6.4 Security & red-teaming

**OWASP LLM Top-10** is the canonical security checklist for LLM apps. Treat it like the regular OWASP Top-10 — go through each, identify your exposure, document a mitigation.

The four most common attacks in practice:

- **Prompt injection** — user input contains instructions that override your system prompt. Mitigations: structured input fences, output validation, separating untrusted text from instructions.
- **Sensitive data leakage** — model echoes back secrets that ended up in context. Mitigations: PII scrubbing on input, output filtering, never put credentials in prompts.
- **Excessive agency** — agent has tools more powerful than it needs (DELETE on a DB, payment authorisation). Mitigations: least-privilege tool design, human-in-the-loop for irreversible actions.
- **Insecure tool execution** — `python_repl` running arbitrary code without sandboxing. Mitigations: subprocess isolation, network egress filtering, resource caps.

Play [Lakera Gandalf](https://gandalf.lakera.ai/) once. The first 4 levels can be done in 20 minutes; you'll learn more about prompt injection than from any reading.
